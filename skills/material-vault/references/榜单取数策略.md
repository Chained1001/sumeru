# 榜单取数策略

## 用途

用户说「查一下最近动漫/漫画/小说的 top20」「看看排行榜前列有什么」时，本文件定：从哪取、怎么判一条算一条、卡上必须记哪几个元信息。

不是给「收一份素材」用的，也不是给「调研一个主题」用的：那两条走 `../workflows/01-采集.md` 与 `../workflows/02-调研采集.md`。

## 一条硬约束：榜单不是「一堆数字」，是「一个有口径的快照」

同一部作品，在不同榜上名次可以差出几百位，而**不代表任何一方错了**——因为口径不同。所以榜单卡上少一个元信息，这条数据就会被误读。

**四个元信息缺一不可**：

| 元信息 | 记什么 | 不记会怎样 |
|---|---|---|
| **榜名** | 哪个平台、哪个榜（如「豆瓣动画分类排行榜」「豆瓣读书 Top250」） | 三个月后不知道这数据哪来的 |
| **时点** | 取数的年月日（榜单天天变，月票榜按小时变） | 被当成长期规律 |
| **排序口径** | 评分 / 热度 / 销量 / 平台加权算法 | 「第 1 名」到底第 1 在什么上，说不清 |
| **过滤条件** | 最少评价人数、是否按作品去重、分类边界 | 114 人评 9.9 的书压过 2301 人评 9.8，还以为它真更受欢迎 |

判据见 `入库判据.md` 的 J-29。

## 选源优先级（这条是实测出来的，不是想出来的）

按这个顺序试，前一层能用就别用后一层：

| 顺序 | 什么源 | 为什么 | 例子 |
|---|---|---|---|
| **1** | **平台自带加权的榜** | 平台已经替你把「评分 + 人数 + 时间」算成一个分，天然不会出现小样本压榜 | 豆瓣读书 Top250（最低也有 5 万人评） |
| **2** | **分类排行榜** | 有明确分类口径与排序规则，但要注意分类边界 | 豆瓣电影分类榜（`/j/chart/top_list?type=25`） |
| **3** | **标签页按评分排序** | 最后手段。**必须自己加人数门槛**，否则满屏几十人评的高分书 | `book.douban.com/tag/漫画?type=S` |

**为什么第 3 层危险**：豆瓣标签「小说」按评价排序，第一页前 20 里有 4 个《红楼梦》不同版本、2 个《三国演义》，而且第 1 名只有 114 人评分。**这不是「最好的小说」，是「评分 9.9 且恰好人最少的那版」。**

## 去重：先定义「一条算什么」

榜单会以三种方式重复同一部作品，**三种都要处理**，且要在取数前就定好规则：

| 重复形态 | 例子 | 处理 |
|---|---|---|
| **同作品多版本** | 红楼梦（中华书局本 / 脂评汇校本 / 大字本） | 合并成一条，取评分最高的版本代表 |
| **同作品多卷** | 镖人 卷一～卷十三、蓝溪镇 1~6 | 合并成一条，取评分最高的一卷代表；人数注明是该卷的 |
| **同作品多形态** | 进击的巨人 最终季 前篇 / 后篇 | **不合并**：是两部独立上映的剧场版 |

第三行是例外，因为「前篇/后篇」是两个独立条目、独立评分，合并会把两部作品的分数混在一起。

## 人数门槛

默认 **≥ 1000 人评分**。理由：低于这个数，评分离散度极大，一个人的差评能把 9.9 拉到 9.0。

用户要「更严格的榜」时提到 5000，要「更宽的榜」时降到 500，但**要说明降到 500 后榜单会开始出现小众条目**。

**门槛是过滤条件，必须写进卡上的元信息**，不能只在对话里说。

## 已知通道能力边界（2026-10-26 实测）

**取数前先查这张表，不要重走死路。**

### 能用的

| 目标 | 通道 | 形态 |
|---|---|---|
| 动漫（动画电影/剧场版） | `movie.douban.com/j/chart/top_list?type=25&start=0&limit=20` | JSON，含 rank/score/vote_count |
| 出版小说、图书 | `book.douban.com/top250?start=0`（每页 25 条） | HTML，含评分与人数 |
| 漫画、绘本 | `book.douban.com/tag/漫画?start=0&type=T`（综合排序） | HTML，**按卷记录，需自行聚合** |
| 豆瓣榜单历史月份 | 在榜 URL 后加 `&updated_at=YYYY-MM-DD` | HTML |

### 不能用的（别试，直接改道）

| 目标 | 现象 |
|---|---|
| 起点 / 晋江 / 番茄 榜单 | 需登录；起点网页返回 202 空内容 |
| 豆瓣短评 | 302 到 `sec.douban.com`（反爬） |
| 萌娘百科各形态 | 只回标题（JS 空壳），API 报 Unauthorized |
| Bangumi、优书网、Fandom | 连不上 |
| 豆瓣「绘本漫画」分类榜 | 只有 3 条，不是 20 条 |

### 需要浏览器才能拿的（有前提）

起点这类 JS 渲染页，宿主工具抓不到，得用本机浏览器 `--dump-dom`（详见「取数通道」一节的降级顺序）。**前提是能启动浏览器**；起不来就如实说拿不到，不改用「我记得」凑。

## 榜单数据的证据性质

这条容易搞错，单独说：

- **名次与分数是「数据事实」**，榜单页就是原始发布方，判据 J-26 路径 (b)，可记「证实」。
- **「为什么排这么高」是推断**，没有原始发布方，必须标〔推断〕，并写清依据（评分人数？类型？）。
- **不要把两者混在一张卡的一个字段里**——复核时分不清哪部分可信。

## 汇总成卡时的三个纪律

1. **一榜一卡**，不把三个榜塞进一张卡。榜是快照，混了就失去时点。
2. **榜单卡上「要点」写「哪个榜、第几、多少分、多少人评」**，不写「很好」。
3. **收完不算完**：要「收集优点」，优点必须另起卡（走 `../workflows/01-采集.md` 的 S-07 或 S-09），并标〔推断〕。

## 停止条件

- 当目标榜单在「不能用的」表里时，停止并如实说明，不硬凑、不编。
- 当过滤后条数不足用户要的数量时，**有几条报几条**，并说明「再放宽门槛会引入几十人评的条目」，不让用户以为榜单天生就这么长。
- 当同一作品在榜上出现多形态（前篇/后篇）且分不清该不该合并时，如实列出两种，让用户定。
