# 10 施工流程

本文件规定由 AI 参与的改动的施工流程：角色、派单门槛、任务打包、审查、记录、回退。只定流程串联，不复写各标准的规则：

| 事项 | 事实源 |
|---|---|
| 提交、分支、提交前检查 | `04-提交与分支.md` |
| 脚本、测试、行为评测 | `02-脚本与测试.md` |
| 文档写法、只写一处 | `06-文档写作.md` |
| 子代理文件的设计 | `07-Agent 设计.md` |
| 版本与 CHANGELOG | `05-版本与发版.md` |

本文的「执行者」「审查者」指会话或上下文，不指人。流程对人与 AI 同样适用。

## 角色

两个角色，按上下文划分，不按模型划分。

| 角色 | 职责 | 禁止 |
|---|---|---|
| 编排（主线程） | 理解需求、判断派单门槛、写派单、派发、收集回执、复核证据、语义审查、决定采纳或打回、提交 | 亲自实现已达到派单门槛的交付物 |
| 执行（子代理） | 按派单完成交付物、返回结构化回执与证据 | 调用其他子代理；改动派单未列出的文件 |

硬规则（约束，脚本不检查）：

1. 同一上下文不得既实现又审查同一交付物。子代理执行的，审查者是主线程；主线程直接执行的，语义审查由人承担。
2. 审查者的工具白名单不含写文件操作，只读审查。发现的问题走整改单，不由审查者顺手修。
3. 主线程是唯一的提交人。子代理不执行 `git commit`。

## 派单门槛

满足以下任一条件，派子代理执行（约束，脚本不检查）：

1. 预计改动不少于 3 个文件，或需新建事实源。
2. 需要读取的背景文件中，与交付物无编辑关系者超过 5 个，上下文隔离有收益。
3. 与其他任务可并行，且改动文件集不相交。
4. 需要受限工具权限：只读、限定站点的联网。
5. 任务性质是审查或调研，需要独立视角或独立产出位置。

不满足任一条件时，主线程直接做，不设子代理。调研类任务不论规模一律派子代理，产出落 `辅助内容/临时文件/`（见其 README），不进交付物。

派单书写成本高于直接完成成本时，即使满足上述条件，也可由主线程直接做（主观判断，由人核对）。

## 任务打包

派单是一段完整文本或一个文件，字段与 `07-Agent 设计.md` 的八节对应。一次性派单不落成 `agents/` 文件，但字段齐全（约束，脚本不检查）：

| 字段 | 对应 07 的小节 | 要求 |
|---|---|---|
| 任务 | 角色 | 一句话说清要什么结果 |
| 上下文 | 无对应，本文新增 | 相关文件的相对路径、事实源指针；不复制文件内容 |
| 输入 | 输入 | 字段、类型、缺失时的处理 |
| 交付物 | 输出 | 显式列出全部目标路径与格式 |
| 约束 | 可用工具 | 工具白名单；默认禁改 `规范/`、`模板/`、`AGENTS.md`、`CHANGELOG.md`，授权时显式写明 |
| 验收标准 | 无对应，本文新增 | 逐条编号，号段用 `A-`，与用例 `C-`、参考件 `J-` 不共用（约定，脚本不检查） |
| 停止条件 | 停止条件 | 何种情况返回已完成部分并标明未完成项 |
| 失败回退 | 失败回退 | 失败时返回哪些字段，不得伪造结果 |

补充规则：

1. 常规派单写目标、约束与验收标准，不写实现步骤；仅当流程固定或有破坏风险时写死步骤。
2. 验收标准至少一条机器可查：命令加期望退出码；其余为可判断语句，写不出阈值时标「主观判断，由人核对」。
3. 回执必须附证据：执行的命令与退出码、写出的文件路径、失败原文。只交总结不交证据，视为未完成。
4. 并行派单的改动文件集不得相交；相交说明任务不独立，改为串行（单写者）。
5. 子代理卡住时做合理假设，写入回执的「假设」字段继续执行，不暂停等待提问；交互式运行可提问。
6. 子代理返回的字段值只作为候选，主线程对关键字段复核后使用（`07-Agent 设计.md` 调用与校验节）。

## 审查协议

两层，机器门禁先于语义审查。

第一层：机器门禁，复用既有检查，本规范不新增：

1. `npm run validate` 与 `npm test` 退出码 0。
2. pre-commit 钩子在提交时运行（`scripts/install-hooks.mjs`）。
3. 门禁不通过时不做语义审查，直接打回并附失败输出。

第二层：语义审查，按固定清单逐项核对（约束，脚本不检查）：

1. 越权：`git diff` 只含派单「交付物」列出的路径；`规范/`、`模板/`、`AGENTS.md`、`CHANGELOG.md` 出现在 diff 中而派单未授权，整单打回。
2. 事实源：新事实只写一处，其他位置为指针（`06-文档写作.md`「只写一处」节）。
3. 测试真实性：断言可观测输出；无占位断言；未删除、未弱化既有测试；新的可观测行为有对应测试（`02-脚本与测试.md`）。
4. 证据复核：回执声称的命令结果由审查者复跑一次；与回执不符，整单不采信。
5. 验收对账：派单验收条目逐条标 通过、不通过、未测；存在不通过即打回。
6. 拿不准的语义条目标「主观判断，由人核对」，转人决定，不默认放行。

审查结论三态：通过、打回（附整改单）、转人。行为评测轮次按 `02-脚本与测试.md` 执行，不在本清单内。

## 记录与交接

| 内容 | 位置 | 依据 |
|---|---|---|
| 改动记录 | `CHANGELOG.md` 的 `[Unreleased]` 段 | `05-版本与发版.md` |
| 测试运行记录 | `辅助内容/测试目录/`，一轮一份 | `02-脚本与测试.md` 行为评测节 |
| 调研、草稿、派单、回执、整改单 | `辅助内容/临时文件/<项目>/<YYYYMMDD>_<目的>/` | 该目录 README |

- 派单与回执是过程产物，不入库、不进 `docs/`；超期清理按临时文件 README。
- 跨会话的大工程用交接文档续接：只写状态、未完项与指针，不复写已在规格、票、提交中的内容。
- 规范或模板被授权改动时，源头、副本、测试同次提交（`00-总则.md`「源头与副本」节）。

## 回退路径

打回时发整改单，内容自包含，原执行上下文可能已丢失：

1. 不通过的验收条目编号与观察事实：哪个文件、哪个命令、什么输出。
2. 期望行为。
3. 原「交付物」路径清单；整改不得新增范围外文件。
4. 有界重试：同一派单打回 2 次仍未通过，停止重试，转人或拆分为更小派单。
5. 回执缺必需字段，或证据复核不实，整单不采信，计一次打回。

## 反模式

以下为禁止项（约束，脚本不检查）：

1. 同一上下文实现并审查同一交付物。
2. 子代理改动派单未列出的文件，或未经授权改动 `规范/`、`模板/`、`AGENTS.md`、`CHANGELOG.md`。
3. 审查者顺手修改被审代码。
4. 无证据的「已完成」声明。
5. 并行子代理写同一文件。
6. 删除、跳过、弱化测试或门禁使改动通过。
7. 把派单全文或规范内容复写进其他文档；写指针。
8. 为流程而流程：不满足派单门槛的改动也走完整派单与审查流水线。

## 变更

修改本文件，同次在 `CHANGELOG.md` 的 `[Unreleased]` 段记录。
