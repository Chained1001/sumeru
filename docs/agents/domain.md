# Domain Docs

工程技能探索代码库时，按这份规则读本仓库的领域文档。

## 动手之前先读

- **`GLOSSARY.md`**（仓库根目录）：本项目特有术语的定义。
- **`docs/技术/技术文档.md` 的「架构决策」表**：按 `D-xx` 编号记的决策。要动的地方若有相关决策，先读它再动手。引用决策时用「与 D-14 冲突」这种写法，编号就是锚点。
- **`docs/产品/PRD.md`**：功能项 `F-xx`、验收项 `A-xx`、开放问题 `Q-xx` 的唯一出处。

本仓库**没有** `docs/adr/`，架构决策不按 ADR 文件存，而是集中在 `docs/技术/技术文档.md` 一张表里。不要去找 `docs/adr/`。

上述文件不存在时**静默跳过**，不提示缺失，也不主动建议新建。

## 文件结构

单上下文仓库（本仓库就是）：

```
/
├── GLOSSARY.md              ← 术语
├── docs/
│   ├── 产品/PRD.md          ← F-xx、A-xx、Q-xx
│   ├── 技术/技术文档.md      ← 分层、数据流、D-xx 决策、R-xx 风险
│   ├── 规范/                ← 上游标准的逐字副本，只读，不改
│   └── agents/              ← 本文件所在处，给工程技能读的配置
└── skills/
```

本仓库没有 monorepo 结构，不存在多上下文，也不存在 `GLOSSARY-MAP.md`。

## 用词按词汇表

输出里提到领域概念时（票的标题、重构建议、假设、测试名），用 `GLOSSARY.md` 里定义的词。不要漂到词汇表明确避开的同义词上。

比如本项目说「素材卡」「索引」「类型」「大类」「私有」，不说「条目」「目录」「分类」「敏感标记」。

要用的概念词汇表里没有，这是个信号：要么你在发明项目不用的语言（重新考虑），要么真的缺一个词（记下来给 `/domain-modeling`）。

## 决策冲突要明说

输出与既有 `D-xx` 决策矛盾时，明确指出来，不要默默覆盖：

> _与 D-14（仓库级与技能级各管各的 CLI 出口）冲突，但值得重开，因为……_

同理，改动若与 `docs/规范/` 的标准冲突，`test/standards.test.mjs` 会因副本不一致而失败——那份目录是上游副本，改标准要改上游再重新复制。
